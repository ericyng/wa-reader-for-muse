2 · First-run: Full Disk Access onboarding

macOS gives apps no way to request Full Disk Access with a prompt — the user has to add the app in System Settings. So the app tests access live (by trying to read WhatsApp's database), deep-links to the exact Settings pane, and detects the grant the moment it lands. No restart, no guesswork.

Welcome to WA Reader for Muse
🔒
Full Disk Access needed
WA Reader for Muse reads WhatsApp's message database on this Mac. macOS protects that file, so the app needs Full Disk Access. Nothing is exported until you grant it.
  1. Click Open System Settings — it takes you to Privacy & Security → Full Disk Access.
  2. Find WA Reader for Muse in the list and switch it on. (If it's not listed, click + and pick WA Reader for Muse from Applications.)
  3. Come back here — this window notices on its own, usually within a few seconds.
Open System Settings Reveal app in Finder ⟳ Checking access…

Why a settings trip? Apple doesn't let apps ask for Full Disk Access with a pop-up — any app that needs it has to send you to Settings. WA Reader for Muse only ever reads WhatsApp's database, and only the threads you choose.

5 · Flows

The four flows that matter: first run, a normal export cycle, the self-healing path for the failure that bit us on Nov 16, and migration from the current setup.

Flow A — First run

1
App launches (login item). It tests Full Disk Access by trying to read WhatsApp's database — the only honest test.
↓
2
Access granted? If not, the onboarding window (§2) opens with the Settings deep-link. The app re-tests every few seconds; the menubar icon stays red meanwhile.
↓
3
Import current setup. The two Stratford groups and the all-chats setting are pre-loaded from today's config — the picker opens as a confirmation, not a blank slate.
↓
4
First export runs. Status flips to "Feed healthy," and the app settles into the menubar. Total hands-on time: one Settings switch.

Flow B — A normal export cycle

1
Trigger. Timer (30 min), a debounced file-system event when WhatsApp's database changes, launch, or "Run export now."
↓
2
Pre-flight. Is WhatsApp running? (If not and auto-open is on: open it, ≤ once per 30 min.) Is FDA still granted? Fingerprint the database (see Flow C).
↓
3
Copy, then read the copy. ChatStorage.sqlite + WAL copied to a private temp dir with a timeout — a stuck copy is abandoned and reported, never left hanging. Only the copy is opened, read-only.
↓
4
Export incrementally. New text messages since each thread's watermark are appended to outbox.jsonl / all-messages.jsonl in today's exact formats; watermarks advance only after the write succeeds.
↓
5
Publish status. status.json + health.json rewritten; menubar state updated. M's checks read these exactly as they do today.

Flow C — WhatsApp rebuilds its database (the Nov 16 failure, self-healed)

1
What happened on Nov 16: a macOS upgrade made WhatsApp rebuild its database; message numbering restarted, so the reader's saved position (17,816) sat above the new maximum (16,534). A healthy reader exported nothing, indefinitely. Fixed by hand that morning.
↓
2
Detection, every run: compare stored watermarks against the live database — if any watermark exceeds the current maximum message number, or the database fingerprint (creation date, message count) changed, treat it as a rebuild.
↓
3
Reset by date, not by number. Watermarks fall back to the newest date already in each output file, and the app re-exports from there. Downstream checks filter by date, so re-exported messages are harmless duplicates — nothing is ever skipped.
↓
4
Log it in plain words: "WhatsApp database rebuilt — export position reset, 227 messages re-exported." Visible in the Health pane and health.json, so the next occurrence is a log line, not an outage.

Flow D — Migration from the current setup

1
Install alongside. The app is built, signed, and installed on m4m. The CLI reader keeps running — nothing changes yet.
↓
2
Grant FDA to the app (Flow A). The CLI binary's grant is left untouched as a fallback.
↓
3
Parallel run. App and CLI both export for one cycle; M diffs the outputs over SSH.
4
Cut over. Disable the wa-reader and wa-health LaunchAgents; the app takes over exports + health. wa-serve keeps serving the same files — consumers never notice.
↓
5
Rollback is one step: re-enable the two LaunchAgents. The old binary, its state files, and its FDA grant stay on disk, untouched, until the app has run clean for a few weeks.
